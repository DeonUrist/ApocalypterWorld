Insanity semantics

The variable is named Sanity, but high values are harmful and passive logic subtracts toward zero. This wiki therefore calls it Insanity in gameplay descriptions.

__GameManager__ :: Sanity

Sleep transaction

Player :: Sleep applies the following immediately when sleep activates:

Fatigue-100
Insanity / Sanity-30
Hunger+10
Thirst+15
Health+40
Drunkenness-100
Weed / alcohol effectsdeactivated

Forced exhaustion sleep is initiated by __GameManager__ :: Fatigue, which writes SleepTime=6 into PlayerCamera :: UseBed and sends Activate to Player :: Sleep.

Insanity mutant spawn loop

__GameManager__ :: SanityMutantSpawn is enabled by the sanity system. Above 90 it waits a random 8–15 seconds, selects an entry from EnemySpawn, and creates it around the player using random X/Z offsets from -25 to +25 and Y +5. The dump also shows weights [0.3, 0.3, 0.3]; exact weighted-selection semantics should be verified before treating them as final effective probabilities.

Health & damage

Health

Player :: Health clamps Health to 0..100. The player-death transition is triggered when Health falls below approximately 0.4.

Fall damage

Player :: FallDamage checks GroundTest.fallingTime. After more than 2 seconds it multiplies falling time by -9 and routes the result into body-part damage.

Radiation

__GameManager__ :: Radiation clamps radiation to 0..100 and warns above 80. The inspected FSM did not itself expose a universal passive radiation gain rate.

Movement & interaction

Player :: Movement has standing, crouching, crawling and running modes. The observed base horizontal/vertical movement multipliers are 2; running uses vertical multiplier 5 and clamps forward input to 5. Player :: Jump handles grounded Jump input through a PlayMaker force action.

Interaction is camera-centric. PlayerCamera :: UseFood ray-picks nearby objects (observed range: 2 units) and handles item-use interaction. PlayerCamera :: UseBed manages sleep duration and the sleep UI.

Items & consumables

Apocalypter items are modular: an item GameObject can carry multiple small FSMs rather than one monolithic item implementation. Frequently observed families include:

Identity

ID, ItemName, image/texture-related FSMs.

Economy

Value, buy/sell eligibility and merchant interaction state.

Consumables

Food, liquid-level FSMs, can/container use and item-use entry points.

Lifecycle

Cook, Perishable, Condition, repair/butcher-related FSMs where applicable.

Many item FSMs exist in the broad runtime dump but their exact action parameters were not present in the filtered detail dump. Do not invent restoration values for an item unless the detailed action or serialized object confirms them.

Spawning & loot

World loot uses many ItemSpawner instances tied to concrete world object paths, often with helper FSMs such as ItemNum. Exact effective probabilities can be nested across count rolls, item-pool selection, weights, and “nothing” outcomes; calculate them only from detailed action parameters.

Example runtime pattern previously observed: an ItemSpawner can carry min/max item counts, use random integer selection, get an entry from an ArrayList, choose a child spawn position and create the item.

Weapons & vehicles

Weapon behavior is composed from PlayMaker families for weapon type, ammunition, reload/chamber state, recoil, aiming and player hand behavior. Vehicle behavior mixes PlayMaker with NWH Vehicle Physics. The player-side bridge is Player :: InCar, which tracks InCarInt/InCarBool and switches movement/headbob/footstep/damage-effect behavior between on-foot and in-car states.

Save & persistence

SaveLoadGame :: SaveLoadGame is the main coordinator. The inspected FSM references Easy Save / ES3, SaveGame1.es3, the world seed, timeline and MapMagic position, and broadcasts save/load-related events. Many world objects also use their own save FSMs, so persistence changes should be audited both globally and per-object.

Evidence & coverage

The source corpus combines runtime FSM dumps, an offline Unity serialized-asset scan, and managed assemblies. The offline scan identified 8,129 PlayMakerFSM components but only 519 were fully decoded by the current generic type-tree pass. Runtime detail remains the strongest source for exact player-system action parameters.

Modding facts

Fifty facts about how Apocalypter behaves at runtime: the coordinate system, object lifecycle, saving, PlayMaker, physics queries and hierarchies a BepInEx plugin runs into, whatever it modifies.

Extraction note: these are facts and observed behaviours collected from mod-development notes, not independently verified findings. Some limitations may be specific to the game's Unity version (2020.3.49f1), its physics configuration, or particular object implementations rather than universal Unity behaviour.

1. World coordinates and object lifecycle

  1. 1

    Floating origin

    The game uses NWH.Common.FloatingOrigin on the Player, with a distance threshold of 1,000 meters.

  2. 2

    Origin shifting

    When the camera moves 1,000 meters from the origin, the game shifts all scene-root objects by the negative camera position during LateUpdate.

  3. 3

    Coordinate instability

    Absolute Unity world coordinates are not stable across floating-origin shifts. The MapMagic root can serve as a stable reference anchor for relative coordinates.

  4. 4

    Object deactivation

    __GameManager__ runs DeactivateFarAwayItems approximately every 5 seconds, deactivating eligible objects more than 1,000 meters from the Player.

  5. 5

    Object destruction

    DeleteFarAwayItems runs approximately every 10 seconds, destroying eligible objects beyond 5,000 meters, including their children.

  6. 6

    Vehicle distance behavior

    Cars are exempt from distance-based deactivation but become kinematic beyond 2,000 meters through DistanceKinematic.

  7. 7

    Distance reference

    These distance-based systems calculate distance from the Player, not necessarily the active camera.

2. Game object registration and persistence

  1. 8

    Object registries

    The game uses NewGO_ArrayList proxies, including ArrayList_Items, ArrayList_Cars, and ArrayList_Sandstorms, to manage registered objects.

  2. 9

    Registration determines persistence

    Only registered objects participate in the game's corresponding save and distance-culling systems.

  3. 10

    Object naming convention

    Newly created objects use names resembling <prefab>(Clone)N, with itemNameID providing a numerical identifier.

  4. 11

    Object initialization

    Certain spawned objects support initialization through a Randomize event.

  5. 12

    Inactive objects and saving

    Inactive GameObjects do not receive the game's SaveGame event.

  6. 13

    ES3 component serialization

    The game's ES3 serialization can attempt to save components attached to persistent GameObjects, including runtime-added components.

  7. 14

    Vehicle-child persistence

    Runtime-added children of vehicles are not automatically persisted.

  8. 15

    Staggered loading

    Saved NPCs, items, points of interest, and equipped backpacks may reappear progressively over several seconds after loading.

3. Save system

  1. 16

    Save framework

    The game uses Easy Save 3 (ES3) with caching.

  2. 17

    Save cache behavior

    Save operations write through an ES3 cache, which is eventually flushed to disk. External file changes made before the flush can be overwritten.

  3. 18

    Active save path

    ES3Settings.defaultSettings.path identifies the active save slot during normal gameplay.

  4. 19

    Load transitions

    The active save path may be empty or stale while a save is loading.

  5. 20

    PlayMaker save variables

    FSM variables such as SaveFile may not accurately reflect the current save slot.

  6. 21

    Save-state transition

    The SaveLoadGame FSM returns to an isPlay state after the save sequence.

  7. 22

    Serialization phase

    The Save_NewGO_ArrayList FSM includes a state named store cached file.

4. PlayMaker and gameplay state

  1. 23

    PlayMaker architecture

    The game relies extensively on PlayMaker finite-state machines for gameplay logic and interactions.

  2. 24

    FSM restart behavior

    PlayMaker FSMs normally restart when their GameObject is re-enabled because Fsm.RestartOnEnable defaults to true.

  3. 25

    Third-person vehicle camera

    Switching to the third-person car camera disables the entire PlayerCamera hierarchy, potentially restarting FSMs underneath it when re-enabled.

  4. 26

    Vehicle attachment initialization

    Certain vehicle-part FSMs start in a CheckTag state that detaches the object from its parent and adds a Rigidbody.

  5. 27

    Pause behavior

    PlayMaker FSMs continue running when Time.timeScale is zero. Some input-processing actions can therefore execute while the pause menu is open.

  6. 28

    Legacy input system

    Gameplay actions use Unity's legacy Input Manager, commonly through PlayMaker GetButtonDown actions.

  7. 29

    Named input actions

    Input axes/buttons include Use, Weapon 1/2/3, Weapon off, Drop Weapon, Reload, Jump, Horn, Use Bandage, Use First Aid, Rotate Item, Change Camera, and Adjust-*.

  8. 30

    Built-in shortcuts

    F2 triggers Heal, F9 hides the UI, and F11 enables God mode.

  9. 31

    God mode behavior

    The F11 mode provides noclip and invisibility, but does not grant invulnerability.

5. Physics and collision detection

  1. 32

    Physics query defaults

    The project has Physics.queriesHitTriggers = true and Physics.queriesHitBackfaces = true.

  2. 33

    Trigger collision queries

    Raycasts can hit trigger colliders, including NPC head triggers.

  3. 34

    NPC head-hit behavior

    NPC head triggers are associated with a 2× damage multiplier.

  4. 35

    Rigidbody collision-query behavior

    Setting Rigidbody.detectCollisions = false can make an object undetectable to raycasts.

  5. 36

    Persisted Rigidbody state

    ES3 persists the detectCollisions property on saved objects.

  6. 37

    Non-convex MeshCollider limitations

    Collider.ClosestPoint on non-convex mesh colliders may return the supplied input point rather than a useful surface point.

  7. 38

    TerrainCollider limitations

    Similar closest-point limitations can affect terrain colliders.

  8. 39

    Overlap-query limitations

    Mesh and terrain overlap queries may detect triangle intersections without recognizing that a point or volume is entirely enclosed by geometry.

  9. 40

    Raycast hit enumeration

    Physics.RaycastAll and RaycastNonAlloc provide a single hit per collider in the observed game environment, rather than every triangle intersection.

  10. 41

    Sweep-query limitations

    Physics sweep queries may ignore colliders already overlapping the swept object's starting position.

6. NPC navigation and vehicle hierarchy

  1. 42

    No prebuilt NavMesh

    The game does not use a baked Unity NavMesh for its vanilla NPC navigation.

  2. 43

    Vanilla NPC navigation

    NPC chase behavior relies on random-walk movement and raycast-based obstacle detection.

  3. 44

    Navigation-related assembly

    AIModule is included with the game, potentially allowing runtime use of Unity's navigation functionality.

  4. 45

    Player hierarchy changes in vehicles

    When driving, the Player becomes a child of a hierarchy resembling <car>/DriveTrigger/sitPos/Player.

  5. 46

    NPC hierarchy changes in vehicles

    Seated NPCs can become descendants of a vehicle, meaning their transform.root points to the car instead of the NPC.

  6. 47

    NPC identity

    NPC hierarchies can be identified by a Health PlayMaker FSM.

  7. 48

    Vehicle identity

    Objects named or marked vehPart and components such as VehicleController can identify vehicle-related hierarchy boundaries.

7. Unity runtime and game architecture

  1. 49

    Scene transitions

    The game destroys ordinary plugin-created GameObjects during scene loading unless they have appropriate persistence handling.

  2. 50

    Game-managed object state

    Vanilla systems may leave temporary modifications on objects, expecting corresponding release or cleanup logic to restore their original behavior.
